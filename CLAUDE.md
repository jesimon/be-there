# CLAUDE.md

Context for working on Be There in Claude Code.

## Purpose
Be There is a Gladspring venture (founders: Jeremy and Suzanne Simon; private): telepresence that lets family, friends and, with consent, caregivers be present with someone who is housebound or far away. Its plan and projections live in the Gladspring planning app (`jesimon/gladspring`, venture id `be-there`); this repository is the product. Benefit first: it exists to make lonely days fewer, not to sell screens.

## The person at home is in charge (never weaken this)
- A visitor can visit only after the person at home approves them on the home screen. Organizers invite; they cannot approve, change drop-in, or pause/resume.
- Drop-in always gives the home screen notice (`DROP_IN_NOTICE_SECONDS`) that can be refused.
- During every visit the home screen shows the visitor's name and a red light, with a one-tap "End visit".
- Nothing is recorded or logged about visits. No analytics. Visitors never see who else visits.
- The rules live in `lib/rules.js` (pure, tested) and are enforced on the server, not only in the browser.

## The relay (never weaken this either)
- Media never passes through our server. A visit always tries a direct connection first, with public STUN only (`stun.cloudflare.com`). The relay (Cloudflare Realtime TURN) is asked for only when a visit has not connected after about 5 seconds, or later drops: each relayed visit leaves usage figures in the owners' Cloudflare account, so most visits must stay off it.
- Relay credentials are made per visit by our server (`lib/ice.js`), only when one of the two devices of a live visit asks (WebSocket `relay`), are sent to the home screen first and then the visitor, and are revoked when the visit ends for any reason: everything goes through `endCallIf`, including deleting the home and stopping the server. At most 4 mints per visit.
- Credentials never appear in `/api/config` (public STUN only, whatever `ICE_SERVERS` holds), in any other HTTP response, in the logs or in storage. `TURN_KEY_ID` and `TURN_API_TOKEN` are set by hand on Render; never put them in `render.yaml` or the repository. Placeholder text in them counts as "not set up".
- A device ends a visit that never connected, or lost its connection for good, with `end` and `reason: 'no_connection'`. The server passes that reason on only for a visit that was answered; any other reason, or a knock still ringing, is passed on as `ended`.
- The home screen says nothing about how a visit is connected (after a visit that could not connect: "The last visit couldn’t connect." for a minute). The visitor page says it in one small line, the only place it uses the word "relay". The organizer page may say "relay".

## The two addresses (never weaken this either)
- Be There answers at `https://bethere.gladspring.org` (new) and `https://be-there-gp50.onrender.com` (the first one), one server behind both. The first must keep working for ever: devices hold their links there, and a browser treats the two as different sites (storage and camera permission are separate).
- Never redirect on the server, never check or act on the Host header, never disable the onrender.com address (no `renderSubdomainPolicy`), and keep the DNS record "DNS only". Every route answers the same at either address; `/healthz` and `/ws` must never get a 3xx.
- The allow-list is in the code: `CANONICAL_ALLOW` in `lib/address.js` (pure, tested). `CANONICAL_ORIGIN` counts only when it is exactly an entry of that list; anything else is ignored with one generic startup line that never repeats the value. `createApp({ canonicalOrigin, canonicalAllow })` exists for tests only; production reads the environment and the fixed list. The hand-off puts link secrets in a URL at that address, so never make the list configurable.
- A device moves only from inside its own page (`public/js/moved.js`, `goToNewAddress(kind, token)`): once, at page load, before anything connects; only when `/api/config` names a `canonicalOrigin` and a WebSocket to its `/ws` opens within 4 seconds (nothing is sent on it); with the secret after the `#`. Otherwise the page stays. The old address's remembered link is never cleared. `moved.js` imports nothing, so an older cached `common.js` cannot stop a page.
- Never move the home screen automatically: `home.js` must not load `moved.js` (a test checks). A camera prompt at a new address must not land on the person at home unannounced. It moves only when a family member opens a new home screen link (which the organizer page makes at the new address) on the tablet.
- Links made on the organizer and setup pages use `canonicalOrigin || location.origin`.

## Photos of visitors (never weaken this either)
- Only the organizer adds, changes or removes a visitor's photo (`PUT`/`DELETE /api/organize/visitors/:id/photo`). Visitors cannot upload, there is no photo route for a visitor's link, and `visitorView()` and every message to a visitor's page say nothing about photos. A photo the organizer adds shows on the home screen straight away; the name always stays in large text beside it. Beside “… is with you” the label is never wider than the screen (a very long name wraps), so the photo cannot push the red light or the name off it.
- The server trusts no upload. `lib/jpeg.js` (pure, tested) checks the JPEG's structure and rebuilds it strictly: a fixed JFIF header of our own first (never bytes from the upload), then only tables, frame and scans; EXIF, ICC profiles, comments, every other APPn segment and anything after the end marker are dropped; a file with an Adobe APP14 marker is refused; at most 4 tables in a quantization segment; every table or part a frame or scan names must have been given. Accepted: 8-bit, 1 or 3 components, baseline/extended/progressive, square, 96 to 512 px, EXIF orientation absent or 1, at most 16 scans, at most 200 KB. No image library; the organizer's browser makes the 384 px square (`squarePhoto()` in `public/js/photo.js`), and the original file is never uploaded.
- A photo is fetched once for each version and never because of a visit. `homeView()` gives each visitor's `photo` tag; the home screen calls `getPhotoUrl()` only when a `state` message arrives, which asks the server only for a tag it has not seen, and keeps the picture in memory (`cache: 'no-store'`, so the browser makes no checking requests of its own). The knock screen and the in-visit label use `cachedPhotoUrl()`, which never asks. A failed fetch is retried by timer only (`RETRY_AFTER`). The host can log request paths, so a photo request at the moment of a knock would be a log of visits.
- Photo responses always carry `Content-Type: image/jpeg`, `nosniff`, `Content-Disposition: attachment`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `Cache-Control: private, no-cache` and `Vary: Authorization`. The home screen reads only its own visitors' photos, with its link secret as a Bearer token.
- Uploads and photo requests are never logged, errors included (the handler after the routes in `server.js` answers them itself, because Express would print them).
- One file per visitor, no history: `photos/<home id>/<visitor id>.jpg` beside `DATA_FILE` (`lib/photos.js`; in memory for a `':memory:'` store, so tests never write into the repository). `store.removeVisitor()` and `store.deleteHome()` delete the files; the visitor's record holds only `photo: { etag, updatedAt }`. An upload takes time to arrive, and the organizer is let in before it does: `store.setPhoto()` keeps nothing and returns null for a visitor removed or a home deleted meanwhile (the route answers 404), so no file is ever left behind for someone who is gone.

## Captions (a trial; never weaken this either)
- Captions are worked out on the listener's device: the home screen's tablet, from the sound it is already playing. No sound and no caption text ever leaves the page that shows it, and none is stored or logged, anywhere. The words go from the worker to its own page by `postMessage` and onto the screen as text; that is the whole of their journey. The one thing kept on the tablet is the person at home's choice (`localStorage` `bethere.captions`: `on` or `off`). `test/captions-page.test.js` lists, word for word, every line of the captions scripts that could send or store anything (`fetch`, `postMessage`, `localStorage`, `caches`, `import()` and more): a new one fails until someone has looked at it and added it there. `test/e2e.mjs` records every message and request the home screen sends during a captioned visit and searches them for the words.
- Home screen only, English only, off by default, switched only by the person at home on their own screen. `visit.js` and `visit.html` must not mention captions, and no message to the server carries anything about them.
- No Web Speech API, ever (`SpeechRecognition` is broken on iPads, cannot hear a visitor's voice, and can send sound to an outside service), and no speech synthesis during a visit (on iOS `speechSynthesis.speak()` mutes the microphone and camera of a live visit). A test checks the captions files and the home screen for both.
- The stack is fixed: transformers.js 4.3.2, `onnx-community/moonshine-tiny-ONNX` (`q8`), Silero VAD, ONNX Runtime Web on single-threaded WASM. **The plain runtime files only** (`ort-wasm-simd-threaded.mjs` and `.wasm`): the "asyncify" build the library picks by itself gets tabs killed on iPhones and iPads. The worker sets `wasmPaths` outright, `useWasmCache = false`, `numThreads = 1`, `allowRemoteModels = false`, `localModelPath` to our own path, and gives the library a fetch that refuses everything but `/captions-files/…` on our own origin. No WebGPU, no COOP/COEP, no Whisper.
- The files (about 49 MB, plus a 2 MB sample) are not in git and not an npm dependency. `lib/captions-files.js` is the list: path, exact address (a pinned npm version or a full Hugging Face revision), bytes, SHA-256. The real server fetches them once in the background when they are missing (`createApp({ captions: { autoFetch: true } })`; never in tests), to a temporary name, verifies size and checksum, renames, and writes `verified.json` last. They live in `CAPTIONS_DIR` or `captions/<version>` beside `DATA_FILE`. `/captions-files/<version>/…` serves only names on the list (looked up in the list, never on the disk), only once verified, as `immutable`. Any change to the list needs a new `CAPTIONS_VERSION` and the same sizes in `CAPTION_FILES` in `public/js/caption-text.js` (a test holds the two together); change transformers.js and the runtime files together; update `THIRD_PARTY.md`.
- The CSP's only change for this is `'wasm-unsafe-eval'` in `script-src`. Do not add `blob:`, `'unsafe-eval'` or another origin.
- **A captioned visit asks the server for nothing once the tablet has the files.** The host can see which addresses are asked for and when, so a request at the start of each visit would be a record of visits (as with photos). The model files and the runtime are kept in the tablet's Cache Storage (`bethere-captions-<version>`). The three scripts captions run from (`captions-worker.js`, `caption-text.js`, `pcm-worklet.js`) are also served at `/captions-code/<id>/…`, where `<id>` names their content (`captionsCodeFrom()`, given to pages as `captionsCode` in `/api/config`) and the answer is `immutable`; `captions.js` starts the worker and the listener from there. The server reads those three files when it starts, so restart it after editing them. The home screen asks `/api/config` when it opens and, while captions are `preparing`, again by the clock: never because a visit starts (a test checks the part of `home.js` between a knock and the end of a visit). The e2e asserts that the second captioned visit reaches the server with no request at all.
- The rules are in `public/js/caption-text.js`, which is pure (no page, network, storage or clock of its own) and tested without a browser: sentences from speech likelihood (512-sample frames at 16 kHz; on at 0.5, off below 0.35; 300 ms kept from before; end after 700 ms of quiet, or 1400 ms when under 1.5 s was spoken; after 8 s a 250 ms pause ends it; never over 14 s), a look at the sentence in progress every 0.8 s of new sound (at least 1.5 times the last look's duration apart, only when under 350 ms behind, only when someone has spoken since), `max_new_tokens = max(8, ceil(seconds * 7))` on clips padded to at least a second, and `createCaptioner()`, which puts them together one block at a time.
- **No raw partial captions.** Of a sentence still being spoken, only the words two looks in a row agree on are shown (`createStableWords()`); words once shown are never changed or taken back, except that the finished sentence replaces its line. The worker never sends a raw partial to the page.
- **The lag cap.** Sound more than 3 s old when its turn comes is dropped with everything waiting behind it, the page says “Captions paused, catching up”, and captions take up again from sound under 0.5 s old. The third time in a visit, or when the model is not ready 90 s after switching on (a first download that is still arriving gets 30 s after its last progress), captions stop for that visit with a plain line and the switch goes off by itself; the remembered choice is left alone. Whatever captions do, they must never throw into, slow or end a visit: `home.js` loads `captions.js` apart from its own script and wraps every call.
- How far behind is the difference between two readings of one clock: the page stamps each block of sound with `Date.now()` and the worker compares its own `Date.now()`. Never `performance.now()` or `performance.timeOrigin` for this: each page and worker has its own, and after days of a home screen being open they need not agree with a worker made today.
- **“On” is put aside while captions get ready.** A tablet that cannot bear the model may close the page, and the visit with it, with no warning. So `captionsOn()` in `home.js` writes `off` before it starts anything, and `on` is written back the first time captions say anything but “getting ready” (they are running, or have stopped themselves), or when the visit ends with them still on. A page that dies while they get ready therefore finds `off` when it comes back, and the next visit does not start them by itself. (A page that dies after they were running still finds `on`.)
- On the visit screen the caption box is above the buttons and beside the small picture; below 800 px of width the switch has a row of its own above “End visit”, and a very short screen gets two lines of captions. The name with its red light and the two buttons are on top of the box (`z-index`), so they stay whole and tappable even if the box did reach them. The switch never wraps (`white-space: nowrap`): two lines made it taller than the room under the captions. The e2e measures eight sizes of screen.
- When a visit ends (`endLocal()`), captions stop: the worker is terminated, the listening nodes are disconnected and the box is emptied. One worker, and so one copy of the model, at a time.
- Messages between `captions.js` and `captions-worker.js` follow the same rule as the WebSocket: add, never rename or remove (an open home screen can get a newer worker).
- `/captions-check` is how the owners find out whether a device can do it, and it must keep using the same worker and the same `startCaptions()` as a visit. Its long test starts its sound inside the tap on the button (before anything is waited for), never waits for ever, and when the page cannot make the sound link to itself it says the test was not run (“Long test not run: …”): that is a fault of the test, never counted as captions failing. Nothing here has run on an iPhone or iPad.

## Architecture
- No build step. Node 20+, Express 5, `ws`, ES modules. `node-turn` is a devDependency used only by `test/e2e.mjs`.
- `server.js`: HTTP API, pages, and the WebSocket switchboard at `/ws` (`hello` → `knock`/`answer`/`decline`/`end`/`signal`/`relay`/`pause`/`approve`/`mode`). Media is peer-to-peer WebRTC; the visitor makes the offer, after the home screen has answered.
- `lib/ice.js`: the public STUN list, the relay's settings, and minting and revoking relay credentials (fetch and the environment are passed in; nothing is logged).
- `lib/address.js`: the one address devices may be sent on to, and the check of `CANONICAL_ORIGIN` against it.
- `lib/store.js`: one JSON file (`DATA_FILE`), atomic writes. Only SHA-256 hashes of link secrets are stored. It also looks after visitors' photos through a keeper from `lib/photos.js` (`createStore(file, { photos })`).
- `lib/jpeg.js`: `inspectJpeg`, `rebuildJpeg` and `acceptPhoto` for visitors' photos. `lib/photos.js`: where the files are kept (`photosInFolder`, `photosInMemory`).
- `lib/captions-files.js`: the list of files live captions need, `captionsStatus()`, `fetchCaptionsFiles()`, `prepareCaptionsFiles()` (the retries) and `captionsCodeFrom()`. `scripts/fetch-captions-files.mjs` (`npm run captions:fetch`) fetches them by hand.
- `public/js/caption-text.js` (the rules, pure), `captions-worker.js` (a module worker: the models), `pcm-worklet.js` (an AudioWorklet: the sound, in blocks of a tenth of a second), `captions.js` (the page's side: `captionsSupported`, `startCaptions`, `openCaptionsWorker`, `showCaptions`, the remembered choice) and `captions-check.js` with `captions-check.html`. `common.js` has `soundContext()` so captions listen through the chime's AudioContext; `home.js` reads `common.js` as a whole for it (`shared.soundContext?.()`), so an older cached `common.js` is not an error.
- `public/`: plain HTML/CSS/JS, one script per page (`home`, `visit`, `organize`, `setup`) plus `js/common.js`, `js/peer.js`, `js/moved.js` (the move to the new address; not used by `home`) and `js/photo.js` (making, fetching and showing photos; used by `home` and `organize`, never by `visit`; it imports nothing). Large type and buttons on the home screen; keep it usable by someone with poor sight or hearing.
- `public/js/peer.js`: the video link for one visit and its timeline (`TIMES`: ask for the relay after 5 s, give up after 30 s, try again after a drop). It takes its timers and `RTCPeerConnection` as arguments so `test/peer.test.js` can run it without a browser.
- Link secrets go after `#` so they never reach server logs.
- The home screen stays open for days, so an old page talks to a new server after every deploy. Keep every existing WebSocket message, HTTP route and `common.js` export working (`makePeer` is kept for this); add, never rename. Pages, scripts and styles are served with `Cache-Control: no-cache`.

## Commands
- `npm start` / `npm run dev`
- `npm test` (unit + server flow + the relay timeline + the new address + photos + captions; the relay is always a fake, nothing calls Cloudflare, the captions files are a pretend list fetched from a pretend site, and nothing is written into the repository)
- `npm run e2e` (two real Chromium browsers with fake cameras, directly and through a local relay, a photo added, changed and removed with every photo request of the home screen counted, captions of a recording of speech with everything the home screen sends recorded, the captions check page, then pages moving between two names for one local server; about two and a half minutes; `SHOTS=dir` saves screenshots). The captions steps run only when the files are on this machine and verified (otherwise it prints `captions: SKIPPED`): `npm run captions:fetch` first.
- `npm run captions:fetch` (fetches the captions files into `data/captions/v1`, or `CAPTIONS_DIR`; about 51 MB; safe to run again)

Every change to the rules or the visit flow needs a test.
